# SmartShield AI — Showcase Replica

A fast, self-contained **showcase build** of the SmartShield AI platform (Adaptive Bot
Mitigation & Traffic Intelligence System Using Deep Learning) written in **Next.js 14 +
React + TypeScript + Tailwind**. It reproduces the full product experience — the live
gateway dashboard, the AI-engine view with the four models, IP intelligence, attack
simulation and four protected demo websites — **with no Python, no servers and no
database required**, so it can be opened on any laptop or deployed to Vercel in one
click for presentations.

> The production system (`../backend`, `../ai-engine`, `../dummy-sites`,
> `../frontend`) runs a Node gateway, a Python/FastAPI engine with real
> scikit-learn/TensorFlow models and four origin processes. This replica implements the
> **same design** — the ten-feature contract, the RF/IF/AE/LSTM ensemble with the same
> weights (0.40 / 0.20 / 0.20 / 0.20), the 0.55 / 0.85 thresholds, the 120 req/min
> per-IP limit and the origin load-shedding model — as a deterministic simulation that
> runs in the browser. Traffic is synthetic; the logic, numbers and UI mirror the real
> stack.

## Run locally

```bash
cd smartshield-replica
npm install
npm run dev        # http://localhost:3100
```

`npm run build && npm start` for a production build. No `.env` is needed.

## Deploy to Vercel

1. Push this repository to GitHub.
2. In Vercel: **Add New → Project → Import** the repo (Framework preset: Next.js is
   detected automatically). Keep the default build command (`next build`) and the
   default **Root Directory** — only when deploying from the full SmartShield monorepo
   set Root Directory to `smartshield-replica`.
3. (Optional) add the two Supabase environment variables below under
   **Settings → Environment Variables**.
4. Deploy. Every push to `main` redeploys automatically. The app is static-first and
   renders in well under a second; the simulation starts in the visitor's browser.

## Supabase (optional)

Attack drills can be persisted as *incidents*. Without Supabase the app behaves
identically — the `/api/incidents` route simply reports `persisted: false`.

1. Create a Supabase project and run this SQL in the SQL editor:

```sql
create table if not exists public.incidents (
  id            bigint generated by default as identity primary key,
  site_id       text not null,
  site_name     text not null,
  kind          text not null,
  route         text not null,
  intensity     int  not null default 0,
  duration_sec  int  not null default 0,
  started_at    timestamptz not null default now(),
  sent          int not null default 0,
  allowed       int not null default 0,
  challenged    int not null default 0,
  blocked       int not null default 0,
  rate_limited  int not null default 0,
  served        int not null default 0,
  shed          int not null default 0,
  shield_enabled boolean not null default true,
  created_at    timestamptz not null default now()
);
alter table public.incidents enable row level security;
```

2. In Vercel (or `.env.local`) set:

```
SUPABASE_URL=https://<project>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service role key>
```

The service-role key is only ever used server-side (route handler); RLS stays enabled.
`GET /api/incidents` returns the 50 most recent rows.

## Demo script (5 minutes)

1. **Landing page** — the pitch, the five-stage pipeline, the four models, what it stops.
2. **Dashboard → Overview** — live KPIs, decision chart, classification donut, risk vs
   thresholds, GeoIP, live request stream (click any row → full decision trace).
3. **AI Engine** — engine status, model cards, the live inference trace, then *Score a
   request yourself* (switch the user-agent from Chrome to `python-requests`, raise the
   rate, remove the cookie — watch the four scores and the verdict change).
   **How it works** — the six-stage flow with live counts, a genuine visitor and a bot
   scored side by side, the live funnel, how bot IPs earn a *malicious* reputation,
   what each model looks for, and the common questions.
4. **Protected Sites** — open the *Direct* link of NorthBolt Bank in a second tab, then
   click **Attack DIRECT** → the bank tab shows its 503 page at once (the first shed
   request flips the origin to DOWN). Stop → UP within about a second. Switch the shield OFF in
   the top bar, **Attack via SHIELD** → still DOWN. Shield ON, **Attack via SHIELD** →
   stays UP while the chart fills with blocks/challenges; open the *Via SmartShield*
   link → the bank works, with the "served through SmartShield" banner.
5. **Traffic & IPs** — the botnet addresses turn *malicious*; click one for its history.
6. **Attack Simulator** — one-click scenarios (credential stuffing, mixed traffic) and
   the live mitigation percentage. **Settings** — move the thresholds/weights and watch
   the pipeline react instantly.

## How the simulation decides

Every synthetic request goes through the same pipeline as the gateway:

1. **Rate limit** — per-IP window, 120 req/min → `429`.
2. **Features** — request rate, session age, header-anomaly score, UA class, cookie,
   Accept-Language count, referrer, method class, challenge token, content length.
3. **Models** — Random Forest (feature-weighted vote), Isolation Forest (rate/header
   outliers), Autoencoder (reconstruction error vs a normal-traffic profile), LSTM
   (burstiness, regularity and path repetition over the client's last 8 requests).
4. **Ensemble** — weighted fusion → risk 0–1 → `allow` < 0.55 ≤ `challenge` < 0.85 ≤
   `block`, each with per-feature contributions and plain-language explanations.
5. **Origins** — each site serves 25 req/s (token bucket with a 1.5 s burst allowance);
   excess is shed with `503`. The origin is DOWN from the first shed request until
   0.75 s after the last one, so a flood takes a site down within a tick and it is back
   within about a second of the attack stopping.

Performance: no external assets or fonts beyond Google Fonts, static pages, charts
without animation, snapshots to React at 2 Hz. Everything is deterministic (seeded),
so the demo looks the same every time.

**Several tabs:** each tab runs its own copy of the simulation, but attack, stop and
shield commands are shared between tabs of the same browser (BroadcastChannel). Open a
protected site in one tab, launch an attack from the dashboard in another — the site
goes down and recovers in lock-step. A tab opened mid-attack catches up immediately.
